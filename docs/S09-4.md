# S09-4: pool generation, snapshots and API commitment

## Scope and implementation plan

This branch starts at S08 P3 (`37097c4`), independently of ongoing P4 work.
It implements the minimal production owners required by S09-4, not the later
project scheduler, transport server, cancellation, or all of E3.

1. Extend `ts_arena::Generation` with one retirement/publication gate. Preserve
   cheap boundary validation, exact checker identity, same-thread reentry
   detection, and retirement during unwinding before releasing a checker permit.
2. Add `ts_project` with a retained program host, diagnostics/query/API slots,
   lazy checker initialization, idle replacement of non-API slots, and immutable
   snapshots sharing a pool. A replacement pool gets a fresh generation; old
   snapshots never switch generations. Program edits alone do not retire a pool.
3. Add `ts_api` with a per-snapshot type registry anchored to the persistent API
   checker. Prepare checker results and serialized response bytes outside the
   gate. Under the gate, validate the exact owner, insert the staged handles,
   publish a shared result and commit the response to a bounded in-memory queue.
   Failure to obtain queue capacity leaves all three uncommitted. No transport
   I/O or caller callback executes under these locks.
4. Registry lookup clones its retained handle under generation then registry
   locks, releases both before taking the checker permit, and revalidates before
   invoking a query. Callback resumption drops/reacquires the operation and
   checks retirement. Panic boundaries close the captured generation.
5. Force both retirement/publication orders, retirement while a registry reader
   waits for a permit, callback retirement/reentry, same numeric type IDs in
   distinct checkers/generations, queue exhaustion, initialization failure, and
   final-root disposal. Run the exact suites in debug/release/Miri/ASan and
   integrate only their scoped E3 criteria.

## Design review before implementation

The accepted authority is ADR 0012 and ownership §2.7. The pin's
`project/checkerpool.go` has separate diagnostics/query slots and a persistent
API checker, while `Project.Clone` shares pools. API registries are per snapshot;
`registerType` keys types by their upstream numeric ID within a project. These
facts require exact checker retention because sibling checkers reuse those IDs.

The gate is acquired before registry/pool/publication locks. No path takes or
waits for an operation permit while holding any of those locks. Lazy checker
initialization and destruction of displaced owners occur outside the gate.
Generation retirement is permanent; storage disposal remains ordinary `Arc`
release. The output queue commitment is the linearization point, not eventual
network delivery. A committed response may be delivered after retirement.

No general `commit(callback)` API is introduced. Exposing arbitrary caller code
under the gate would permit reentry, transport stalls and lease-drop deadlocks.
A guard dropped during unwinding closes the generation while still holding its
gate. Pool initialization failures cannot publish a partially built owner.

New owners live above `ts_checker` to avoid rewriting the S08 algorithm surface.
They use the existing std locks consistently; migrating the workspace to the
ADR's eventual parking_lot choice is not necessary for this ownership contract.
Scheduling affinity, idle timers, symbol/node wire endpoints and protocol error
encoding remain later server work; the type registry exercises the actual
checker retention boundary without inventing wire metadata.

## Verification record

Implemented in `ts_arena`, `ts_project` and `ts_api`, without changes to
checker algorithms. The exact inventory has 27 tests: nine generation/lease,
nine pool, and nine registry/publication tests. Pool and registry tests assert
final `Weak` roots and tracked storage counts, but E3's aggregate live-counter
metrics retain their original S04 scope; these are not heap measurements.

The independent implementation review found and fixed the initialization retry
window (retirement now occurs inside the `OnceLock` initializer), same-thread
initializer reentry, snapshot birth validation, and request-boundary placement.
The registry contention test observes an actual `WouldBlock` on the production
checker permit before a sibling retires; it does not infer contention from thread
startup. The opposite ordering is also forced inside the actual API commit:
retirement observes `WouldBlock` while commitment is paused immediately before
the real queue append, then completes only after publication. Initializer failure injection runs inside the real initialization cell;
its test makes no claim about a forced simultaneously waiting initializer.

The type registry is the minimal concrete API retention owner in this slice.
It does not claim signature/symbol/node registry endpoints or full wire parity.
The output queue commits pre-serialized bytes, with no transport under its lock.

Debug tests, changed-crate clippy with warnings denied, formatting and Rust 1.96
checks pass. The registered E3 capture passed every declared suite in debug,
release, Miri with strict provenance, and AddressSanitizer. All 27 S09-4 cases
passed in each mode; both `shared_pool_panic_retirement` and
`release_boundaries` are true. The capture also reran the existing arena, AST,
binder and program ownership prerequisites; no emitted metric is false.
