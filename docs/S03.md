# S03: generators from the pinned schemas

S03 establishes reproducible schema exports and Rust generation under
[ADR 0015](adr/0015-generated-code-from-the-pinned-schemas--with-upstream-s-extr.md). The pinned Go and
TypeScript extractors remain authoritative. A separate tooling worktree carries
the access adapters; `upstream/` remains the untouched source and client used
for comparison.

## Implementation plan

1. Create an independently managed tooling repository and detached worktree at
   the ledger's upstream pin. Apply the checked-in patches from
   [`tools/s03/patches`](../tools/s03/patches) and copy the adapter entry points
   into that worktree. Do not patch the canonical oracle source.
2. Run upstream's `SchemaAPI` to export resolved kinds, bases, node properties,
   child order and visitor behavior. Use its encoder analysis and diagnostic
   generator to export their resolved data rather than interpreting the input
   schemas a second time.
3. Generate Rust syntax kinds, payloads, accessors, visitors, diagnostic
   messages and encoder layouts. Preserve signed source positions and explicit
   child identities. Inventory storage and custom codecs that require later
   runtime ownership instead of filling those gaps with successful stubs.
4. Extend `gen-proto` with a JSON export of its discovered methods and rendered
   wire metadata. Reconstruct the client TypeScript using that JSON alone;
   format it with the pinned formatter and compare its bytes with the original
   checked-in client. Regenerate Go-derived enums with upstream's extraction task. Inventory the five
   handwritten enum declaration/runtime pairs separately as source inputs;
   compare all client files without crediting those inputs as regenerated.
5. Generate into a staging directory, compare the complete output inventory,
   and register measured patch, schema, drift and client results. Exercise the
   producer's failure paths and run the workspace, lint and sprint gates.

## Generated surface and boundaries

| Surface | Source of authority | S03 output |
| --- | --- | --- |
| AST | Pinned `tools/scripts/tsc/schema.ts` resolver | [`tsr_ast`](../crates/tsr_ast/src/lib.rs): 351 syntax kinds and 192 schema node payload variants, schema-kind-checked construction, typed accessors and immediate-child visitors/mappers. |
| Diagnostics | Pinned message generator and `diagnosticMessages.json` | [`tsr_diagnostics`](../crates/tsr_diagnostics/src/lib.rs): 2,211 message identities, codes, localization keys, categories, flags and default text. |
| Encoder | Pinned encoder schema analysis and Go constants | [`tsr_encoder`](../crates/tsr_encoder/src/lib.rs): 28 protocol constants and 192 node layouts covering all 351 kinds, ordered child fields, packed common-data fields and custom-codec requirements. |
| API | Patched pinned `tools/gen-proto` | `api.json`: 142 method IDs, 128 named types, 105 DTO declarations and 14 special mappings, including original tags and result annotations. |
| Client | Exported API contract and pinned enum generator | Reconstructed `proto.generated.ts` and regenerated enums checked against the untouched client's bytes after the pinned formatter. |

The AST payloads contain non-retaining node IDs and owner-qualified list ranges.
Their generated visitors preserve child order, list boundaries and early exit.
A range describes child IDs; it does not uniquely identify a list instance.
The future list owner must preserve each list’s source range and modifier flags,
including distinct empty lists. Constructor checks certify the schema’s kind
constraint, not ownership, required children or readiness for encoding.
An owning parser/tree must later validate and resolve those ranges. Schema
fields needing binder symbols, flow handles or checker state are
explicitly deferred in generated metadata. Handwritten SourceFile runtime state
also remains future work. Every Go node/list pointer stays optional in Rust:
for example, DefaultClause.Expression may be nil despite schema optional=false.
The generator does not claim to implement those fields’ storage or lifecycle.
Parsing, list storage and recursive traversal remain S06 work.

Encoder tables describe the wire layout, including custom-layout requirements;
they do not encode a file yet. Diagnostic production, formatting and locale
selection also remain later compiler work. S03 does not complete E1 or claim
runtime AST/encoder parity.

The API JSON exporter observes `gen-proto`'s existing dispatch discovery,
nullable/result annotations, `jsonField` decisions and named-type renderer. The
JSON-only client renderer uses exported declaration order, aliases, prepared
documentation and wire spellings. It never reads Go source or copies the
original TypeScript file. The original generator's TypeScript output is also
checked as a control. The comparison covers 69 client files: 59 generated outputs
and ten handwritten enum files retained as source inputs. The latter
are explicitly listed in [handwritten-enums.json](../data/s03/handwritten-enums.json).
Every generated enum output is removed before generation so the original
checkout cannot hide an omitted output. The five handwritten pairs are absent
from the pinned enum task. They are not safely reproducible from one another:
for example, CharacterCodes.ogham is 5760 in the declaration and 5765 in the
runtime file at this pin. S03 preserves that existing source discrepancy; it
does not change the client baseline or count those files as generation evidence.

[`api-special-codecs.json`](../data/s03/api-special-codecs.json) inventories every
observed special mapping and custom serializer. It links 36 representative
pinned-Go wire observations to ordinary omission/null rules, numeric IDs,
tristate, document identifiers, raw JSON, ordered maps, enum values and batch
responses. These fixtures preserve source behavior for later Rust API tests.
Error snapshots preserve the JSON library's semantic/syntax classes, concrete
Go error and value types, byte offsets, JSON pointers and exact underlying
causes. The pinned library deliberately varies its top-level error wording
between processes; that full rendering stays in captured stderr rather than
the deterministic fixture. Unknown error reasons remain exact, so unrelated
failures cannot pass through broad text normalization.
They do not establish Rust API codec parity: custom batch pre-encoded responses
and complete nested JSON behavior still require runtime tests when those
implementations arrive. A TypeScript `number` does not authorize storing Go
`uint64` identifiers as Rust `f64`.

## Reproduction and prerequisites

Initialize the pinned source before generation:

```sh
git submodule update --init upstream
cargo xtask gen
cargo xtask gen --check
cargo xtask run gen
cargo xtask status
cargo xtask check S03
```

`cargo xtask gen` writes reviewed generated outputs. `--check` regenerates and
fails on output drift or client differences. The registered producer uses
`--verify` to retain measured results for the tracker; successful capture alone
does not mean its metrics passed.

Node and npm versions come from `volta` in the pinned
[`upstream/package.json`](../upstream/package.json); its `packageManager` pin
must agree. The upstream lockfile pins the TypeScript compiler and formatter.
Go uses the existing [`toolchains.toml`](../data/s04/toolchains.toml), with
`GOTOOLCHAIN=local` so the evidence cannot silently use a downloaded replacement
compiler. The generator checks the actual executable versions.

The disposable checkout lives under `.s03-tooling/pin`, with independent
Git metadata under `.s03-tooling/upstream.git`. These stay outside `target/`:
Rust cache cleanup removes non-Cargo files there, leaving unusable partial Git
repositories on the next restore. Legacy tooling remnants under `target/` are
not reused. The producer provisions its npm
dependencies with `npm ci --ignore-scripts`. Caller Go and npm download caches
remain reusable outside `target/`; an offline run still needs those dependencies
and the exact tools provisioned. For local bootstrap, the driver also recognizes an exact Node/npm installation
at `target/s03-runtime/node_modules` (created with
`npm install --prefix target/s03-runtime --no-save node@24.20.0 npm@11.17.0`).
These versions must still match the upstream package pins.
Regeneration never installs dependencies into
the canonical upstream checkout.

## Evidence and failure handling

| Metric | Required observation |
| --- | --- |
| `run.gen.patches_apply` | All carried patches apply to a clean tooling worktree at the pinned revision. |
| `run.gen.ast_schema` | The pinned resolver executes and its normalized AST export passes structural checks. |
| `run.gen.drift` | `false` only when regenerated outputs and their complete inventory match the committed artifacts. |
| `run.gen.client_identical` | Export-derived API TypeScript and regenerated enums are byte-identical to the untouched client after the pinned formatter. |

An executed AST resolver that fails or leaves missing/empty normalized tables
records `ast_schema: false`, with client and drift metrics absent because those
stages did not run. Missing tools, unreadable files and malformed JSON fail
capture. Rust emitters additionally validate the exported shapes before drift
can pass. Named producer output and captured stderr identify the failed stage.
The client comparison rejects missing or extra files as well as changed
bytes; deterministic output alone would not prove agreement with upstream.

The generation fingerprint includes the three generated crates, every workspace
package manifest, the emitters, adapters, schemas and tool configuration. Editing
the text or arena implementation alone does not invalidate generation evidence;
their dependent build and quality evidence must still be refreshed. Generated
Rust is formatted using the workspace's declared edition.

Each attempt uses a fresh stage under `target/`. A lock spans both frontend work
and Rust emission/publication, so a concurrent generator cannot delete an active
attempt's inputs. Starting the next attempt prunes older stage directories and
retains only the current attempt, including its files on failure.

The four native CI targets run generation independently of E3 and E4 capture.
Node/npm installation or another producer failure does not skip unrelated
quality checks, source evidence or artifact upload once tracking validation
has succeeded. CI restores npm's cache using the upstream lockfile and Go's
module cache using both the `tsc` and tooling module checksums. S03 closure is a
required gate; the full parser experiment remains deferred to its own sprint.

The exporter tests check result overrides, nullable annotations, request-array
metadata, nonnil fields, custom-codec inventory, determinism and preservation
of the original generator output. JSON client-renderer tests reject duplicate
keys, duplicate method/types, unsupported schemas and missing declarations.
Rust checks cover generated constructor/kind compatibility, visitor behavior,
diagnostic lookup and encoder metadata. Full producer evidence and its source
hashes are recorded through the normal tracker commands above.
