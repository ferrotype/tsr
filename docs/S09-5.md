# S09-5: complete ownership execution and final-drop checks

S09-5 consumes the whole E3 experiment, not only the two instrumentation flags
or the seven S04 counter scenarios. The combined producer is
`scripts/s08_ownership.py`: it runs the S04/S06/S07/S09 suites and then the S08
independent-checker merge observations. Every required suite executes in debug,
release, strict-provenance Miri and AddressSanitizer. The current S09 inventory
contains 51 tests; the S06 AST-storage inventory contains 30.

## Counter scope and proof

`live_owner_delta` and `live_allocation_delta` are numerical measurements from
the seven S04 scenarios. They are not numerical aggregates over every later
test. The experiment's metric descriptions now state that scope explicitly.
The additional required criteria carry their own disposal assertions:

| Ownership boundary | Existing final-drop observation | Required criterion |
| --- | --- | --- |
| File, lazy, bundle and scratch storage | S04 measured before/after counts, plus S06 retained-node, mapped-node, imported-bundle and unwind assertions | S04 ownership criteria; `ast_runtime` is also enforced by CI and the S06 prerequisite |
| Shared files and retained edit responses | Both program ownership tests compare final `Counts` with the empty baseline | `shared_bound_file`, `retained_snapshot_edit` |
| Independent checker merges | Native query/merge parity plus retained-result lifetime observations checking program release after the last result drops | `independent_checker_merges` |
| Pool, snapshots and registry | Per-test final `Counts` assertions and exact `Weak` root checks, including retirement and publication races | `shared_pool_panic_retirement`, `release_boundaries` |
| Retained results and checker AST | Final counter snapshots and checker/program weak roots after all handles drop | `checker_result_retention`, `checker_ast_retention` |
| Builder generations and emit metadata | Counters step down as roots drop; every test returns to its initial snapshot | `builder_cache_retention` |
| API print and insertion scratch | Counter equality after successful, returned-error and unwind paths, including repeated requests | `api_scratch_disposal` |

The observations live in `ts_arena::scenarios`, `ts_ast::storage_tests`,
`ts_compiler::ownership_tests`, the P2 checker adapter, `ts_project`'s pool and
retention suites, `ts_checker::node_builder::cache::retention`, and `ts_api`'s
registry and scratch suites. Low-level identity and lock tests supplement these
lifecycle scenarios; not every supporting unit test is a separate allocation
measurement.

Thus a zero S04 delta alone cannot complete S09-5: its `exp.E3.pass` condition
also requires every later criterion. An assertion failure, missing test,
unexpected test or ignored test prevents the corresponding suite from passing.
The producer does not manufacture a larger numerical aggregate from successful
test counts. These counters cover tracked owners and storage allocation units,
not all heap bookkeeping or RSS; neither is required to return to baseline.
