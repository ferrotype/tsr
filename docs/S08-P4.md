# S08 P4 — body checking and dependency closure

P4 starts on PR #19 at `37097c4`. This record covers implementation in progress;
it does not certify P4 or the E2 denominator. P5 will be stacked on the completed
P4 PR, followed by the remaining checkpoints in the implementation plan.

The acceptance inventory remains the frozen 9,369 primary variants. Informational
variants stay separate under the approved S07-3 amendment. The declaration
diagnostics path remains required: a requested phase that has not executed is a
pending failure even when the expected diagnostic list is empty.

Implementation order:

1. Connect ordinary expressions and function bodies to the existing type engine.
   Add binder-graph reachability, flow facts, narrowing and definite assignment
   together with return inference; enable TypeQuery through those production paths.
2. Complete value declarations, classes, enums, modules and JavaScript/JSDoc
   dependencies, including alias resolution and the loaded library closure.
3. Complete calls, contextual expressions, statements and grammar across the frozen
   option sets. Run every primary variant and retain a replayable failure inventory.
4. Implement declaration diagnostics through the declaration transformer and the
   checker emit resolver; keep phase execution visible in the runner.
5. Resolve the remaining inventory and lazy-library fixture failures, verify the
   frozen relation actions and ownership/error cleanup, then open the P4 PR.

Independent work is divided by module: return inference, enums and the corpus
driver can progress alongside expression/flow integration. Native fixtures measure
their combined behavior; component fixtures do not substitute for the corpus gate.

Performance evidence and full byte/display acceptance remain at their named later
checkpoints. No thresholds, eligibility predicates or approved divergences change.

## Implementation record

The first full execution inventory used an immutable earlier P4 binary and source
snapshot while implementation continued. Its authenticated replay covers all
10,728 variants: 9,369 acceptance and 1,359 informational. In that snapshot,
6,185 acceptance variants executed semantic diagnostics, 3,023 reached named
failures, and 161 panicked before that phase. Only 5,433 completed all requested
diagnostic phases; declaration serialization was still absent. The corresponding
informational counts are 932, 413, 14, and 827. These are execution counts, not
Go/Rust parity counts, and they do not describe the current source revision.

The capture is retained under `target/s08/p4-inventory-01`; its capture manifest
SHA-256 is `f251dd64c0651536ee57ecac85ef19375517f819410d0e1ea2682cd2668e653c`.
`final-summary.json` ranks the old blockers, and `report.json` retains each
variant's phase outcomes. The later refresh must use a new immutable snapshot.

Focused native comparisons have closed all 420 frozen P0 relation actions and
90 downlevel/options programs with 90 queries. The latter cover private elements
at ES2021/ES2022, both class-field definition policies, imported helpers,
CommonJS generated names, anonymous class naming and retained NodeNext `tslib`
resolution. These checks do not replace the full execution inventory or E2.

Declaration work now includes the production `Program` phase, a declaration
transformer, accessibility and reference-resolver adapters, generated names,
JavaScript/CommonJS collection, and syntactic pseudo-type inference. The
standalone pseudo checker matches 850 native complete-tree observations; a
4,000-level const tuple test exercises construction and release on a 512 KiB
stack. Semantic pseudo-type equivalence, annotation reuse and temporary lexical
scope integration are being verified together through declaration diagnostics.
An error reported by the native builder can return no output node; the resolver
preserves that result, and each transformer caller applies its native fallback.

Serialization scopes use checker-owned synthetic nodes and binding tables, with
source parents retained explicitly. They never mutate a published file. Their
allocations are included in the checker census. Unlike the native per-builder
scope links, the current Rust scope records live until the checker generation is
dropped; P7 must measure this retention under repeated display/emit requests.
