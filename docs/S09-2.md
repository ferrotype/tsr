# S09-2: builder caches and emit side tables across generations

## Scope

One E3 criterion, `builder_cache_retention` (ownership note, sections 2.6 and
4): clone cached A into B, remove A's cache entry and rotate allocation; B's
original links still resolve A; generation ids differ; storage is reclaimed only
after all cache, side-table, dependent-handle and factory roots drop.

## How the contract is implemented

The mechanism came with S08 P5 and is unchanged. The note describes a builder
arena whose allocation generation rotates on `release`. The implementation
reaches the same contract with request frames:

- A generation is one request. It builds in its own arena and, when it has
  reusable entries, is published as one `AstFile`. Every cache entry it produced
  owns that file, so the entries are the cache roots.
- A cache hit clones the cached syntax into the current frame, records the
  `original` links, and makes the current frame retain the file it cloned from.
  A published frame therefore carries its closure, and B keeps A alive without
  either arena owning the other.
- The emit side tables are persistent and keyed by non-owning ids. They are
  swept when the last construction frame ends. The sweep keeps an entry whose
  node some cache root still retains, directly or through a closure, and refuses
  to leave a live key with an unretained `original` target rather than let the
  link dangle.

The one production change is a refactor: the sweep moved out of
`release_cached_frame` into `CachedBuilder::sweep`, with no behaviour change.

No production path evicts a cache entry on its own, and the pin never does. Two
removal forms are exercised. The natural one is replacement: an outer request
serializes a key, a nested request publishes the same key first, and the outer
request then publishes over it. The direct one is a test-only
`CachedBuilder::remove`, which removes one entry and runs the production sweep,
so the contract is pinned down for the day an eviction policy exists.

One observation the tests record rather than assume: generation B owns two
entries, not one. The nested property type is serialized under the nested flag
context, so it misses A's key, and the clone of A comes from a hit on A's own
key in the same request. The tests treat every entry of a generation as a root
of it.

## Suite

`data/s09/ownership-cases.json` inventories four tests in
`crates/ts_checker/src/node_builder_retention_tests.rs`, filter
`node_builder::cache::retention::`, scored as `builder_cache_retention`.

- After A's entry is removed, nothing is reclaimed, B's frame still resolves
  A's node, the side table still maps the clone to its original, and a rotated
  generation that hits B reaches A through the chain of retained frames. The
  three generations have three different arena ids. Removing B's entries
  reclaims both generations and leaves no side-table entry.
- The nested-publication replacement: A's entry is replaced by the outer
  request's node, A has no cache root left, the final sweep accepts the clone's
  link because B retains A, and the replacing generation cannot resolve A.
- Cache roots first, then a returned frame, with a factory still active: nothing
  is reclaimed and the active frame still resolves A and the clone's link. When
  the request ends with nothing to publish, every generation is reclaimed and
  the side tables are empty.
- Factory first, then B's cache roots, then the returned frame, then A's entry:
  the counters step down generation by generation, B only after its last root
  and A only after its own.

Counters return to baseline in every test.

## What the suite does not claim

The side tables are not owning roots in this implementation: they follow the
cache roots through the sweep. A returned frame retains storage but not the
persistent metadata of its keys, and the last test asserts exactly that. Display
returns text, so no production caller holds such a frame today; the explicit
`TypeNodeBuilder` owns its own emit context for its whole lifetime.

## Verification record

All four tests pass in debug, release, Miri with `-Zmiri-strict-provenance` and
AddressSanitizer with a rebuilt std, through the producer's exact command form.
The six existing cache tests still pass after the sweep refactor. Two mutations
confirm the suite can fail: a cache hit that does not retain the frame it clones
from fails all four, and a sweep that keeps every side-table entry fails three.

The producer publishes `builder_cache_retention` with per-mode outcomes,
independent of the S09-1 and S09-4 criteria; 48 producer tests pass. Changed-crate
clippy with warnings denied, formatting and `cargo xtask validate` pass. No E3
evidence is recorded by this change.
