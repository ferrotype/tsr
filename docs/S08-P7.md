# S08 P7 — Required measurements: implementation

P7 owes the frozen measurements of the S08 plan (§6, `docs/S08-implementation-plan.md`):
the checker workload comparison (`data/s08/checker-workload.json`), the per-type
footprint census (`data/s08/type-footprint.json`) and the isolated relater
comparison (`data/s08/relater-fixtures.json`). This record covers the
implementation of the measurement adapters and the reference relater on
`codex/s08-p7` (based on `codex/s08-p6` at `619a59e`). It does not contain the
required measurement itself: that is one explicit capture on the designated
quiet native host, which the owner runs. Every number below comes from bounded
development-host smoke runs and shows only that the pipelines work end to end.

## Checkerbench

### Executables

- Rust: `crates/ts_compiler/examples/p7_checkerbench.rs` over the shared
  diagnostic executor and the P5 walker, built three ways from
  `crates/ts_compiler/Cargo.toml` features. The normal timing binary has no
  feature: no observer, no phase clocks, no allocation counting. `s08-phase-timer`
  compiles `tools/s08/p7/instrument.rs`, nested exclusive clocks for
  initialization, checking and display. `s08-allocation` compiles the S07 `cap`
  wrapper around mimalloc (requested and live bytes at the allocator boundary;
  `cap` counts no allocation calls, reported as unavailable) and enables the
  checker's `storage-pilot` census.
- The executor (`tools/s08/p4/executor.rs`) takes a `Hooks` object. The interval
  starts after loading, parsing, binding and the loader-graph observation; every
  diagnostic JSON conversion inside it is bracketed by `pause`/`resume`; checker
  construction (`CheckerOwner::for_program` and the operation) is the `init`
  phase; the checkpoint runs after the complete schedule with the checker and
  every result live. The P5 corpus observer (`tools/s08/p5/corpus.rs`) pauses
  around the error-baseline rendering (baseline decoration) and passes the
  walker's retained `GetTypeAtLocation` results as roots.
- The walker (`tools/s08/p5/baseline`) has a count-only recording mode: the
  checkerbench child counts operations instead of building query JSON inside the
  interval, and wraps `TypeToTypeNode`+printer, `SymbolToStringEx` and the public
  `TypeToString` display in the display clock (child display time is subtracted
  from the enclosing check clock).
- Go: the E2 baseline overlay (`scripts/s08_baselines.overlay_sources`) plus
  `tools/s08/oracle/checkerbench/`: a clock in package `core`, the checker
  construction hook in `checkerpool.createCheckers`, a compile hook that replaces
  the harness's pre/post double compile with one program, `BindSourceFiles`
  before the interval and the pre-emit diagnostic sequence inside it (the frozen
  E2 comparison established that Rust's single non-emitting pass produces the
  same diagnostics), count-only query recording, display clocks around the same
  three display sites, retained roots and `S08FamiliesCensus` at the checkpoint.
  `S08_MODE` selects normal, phase or alloc. `TS_TEST_PROGRAM_SINGLE_THREADED=1`
  keeps one checker.
- Both children hash the same produced bytes after the interval (types and
  symbols baselines, error baseline, public type strings, the sorted
  deduplicated diagnostics as code:file:pos:end) and report the executed action
  counts per variant. The driver requires identical action counts per variant
  across runtimes and identical output/action digests across a runtime's own
  samples; cross-runtime digest agreement is reported per variant.

### Driver

`scripts/s08_checkerbench.py`: `build` (three release Rust binaries with exact
Cargo artifact selection, one Go test binary compiled with the overlay),
`capture` (the acceptance requests from the current E2 corpus capture checked
against `data/s08/baseline-requests.json`; per executable kind one warmup Go
then Rust, then seven alternating fresh-process samples in the frozen order),
`report` (median-of-seven ratios, max/min > 1.10 stability flags, phase sums,
allocation and retained bytes with positive Go denominators, the census
statistic as the median over samples of aggregate type-storage bytes per
reachable type) and `producer`, declared as `[checkerbench]` in
`status/runs.toml` (`run.checkerbench.throughput_ratio`,
`allocated_bytes_ratio`, `retained_bytes_ratio`). `run.e5.type_footprint_ratio`
joins the E5 producer from the same capture through
`s08_checkerbench.footprint_metric`. A smoke or source-stale capture yields no
metrics.

### Smoke run (development host, 5 variants, 7 samples, not the measurement)

All five variants matched Go on output digests and action counts in every
sample. Development-host medians of the per-sample totals:

| quantity | Go | Rust | ratio |
|---|---|---|---|
| checker interval, normal timing | 2.24 ms | 9.78 ms | throughput 0.23 |
| phase init / check / display (median totals) | 1.10 / 0.75 / 0.44 ms | 5.10 / 2.30 / 2.51 ms | |
| requested bytes in the interval | 2.15 MB | 7.47 MB | 3.47 |
| retained bytes at the checkpoint | 1.30 MB | 2.22 MB | 1.71 |
| type storage per reachable type (census) | 168.7 B | 195.2 B | 1.16 |

Observations to carry into the real capture: checker initialization dominates
the Rust interval on tiny variants; the Rust census reports every created type
as reachable (552 created, 552 reachable) where Go reaches 354 of 472; Rust
`symbol_tables` capacities differ between processes (hash-table growth), so the
census statistic is a median with its spread; Go's `checker_ast` family stays
unavailable (the plan's rule: unavailable, never zero). The footprint gate
(≤ 0.80) is missed on this smoke set.

## Per-type footprint

`Operation::census` (`storage-pilot` feature) exposes the P1/P3 census with the
walker's retained types as roots; the Go side uses `S08FamiliesCensus` on the
program's single checker with the same roots. Both run at checkpoint 2 in the
allocation executables only. The aggregate mean over all variants is
`sum(type_storage_bytes) / sum(types.reachable)` per runtime, Rust over Go.
Unreachable occupied records stay in the numerator; a failed census on any
variant makes the statistic unavailable.

## Relater

### Reference prototype

`tools/s08/relater-prototype` keeps its P1 construction and mutation API (strong
`Rc` cells owned by the graph, `Weak` edges, `OnceCell` lazy structure, consumed
resolvers, explicit `Released`/`ResolutionFailed`/`UndeclaredMember` failures,
`#![forbid(unsafe_code)]`) and now carries intrinsics, literals (fresh and
regular forms), unions, intersections and object types with properties, index
signatures and non-generic call/construct signatures. The algorithm ports the
pinned `relater.go` paths for those kinds: `isTypeRelatedTo`,
`isSimpleTypeRelatedTo`, `isRelatedToEx` (with the common-property and weak-type
checks), the union/intersection family, `recursiveTypeRelatedTo` with recursion
flags, expanding flags, deeply-nested identities, the complexity budget and the
maybe stack, `structuredTypeRelatedTo` with the intersection extra passes,
properties (unmatched, optionality, readonly, identity), signatures
(`compareSignaturesRelated` for non-generic signatures with callback
bivariance, identity) and index signatures (applicable infos, member inference,
identity). Paths that would need generic instantiation, inference,
conditional, mapped, template-literal or tuple machinery fail explicitly with
`Error::Unsupported` and are reported, never approximated. Every
`checkTypeRelatedTo` outcome is recorded (the Go observer's `ternary_calls`),
one diagnostic chain is emitted per failed reported relation.

A [`Description`] is the prototype's input: a plain snapshot of types (flags,
object flags, symbol and alias identities, literal values, members with their
optional/readonly/class-member bits, index infos, signature shapes, union and
intersection constituents). `Graph::construct` allocates every cell, links
union constituents after all cells exist and gives every object a lazy resolver
that materializes members, index infos and signatures on first use (counted as
`lazy_records`).

### Comparison child

`crates/ts_compiler/examples/p7_relater.rs` (`relation-probe`, optionally
`s08-allocation`) runs one ordered pass of the 21 frozen fixtures, five mode
groups each, on a 256 MiB worker stack. Per group: a fresh production checker,
the A/B declared-type lookup (setup), then the four actions (relation interval).
`--implementation id` relates through the production relation probe.
`--implementation reference` additionally translates the reachable production
types into a description (new read-only `Operation` handles: `index_infos`,
`signatures_of_type`, `signature_shape`, `literal_shape`, `is_readonly_symbol`,
`alias_symbol`), constructs the prototype graph inside setup and relates in the
prototype. Setup and relation intervals, their requested bytes and live bytes
before/after each group are recorded separately.

`scripts/s08_relater.py`: `parity` compares both implementations with the frozen
Go observations (`data/s08/supplemental-observations.json.xz`, request digest
checked against the archived request inventory): the ID side exactly (results,
ternary calls, before/after counters and caches, diagnostics); the reference on
results, ternary calls, the cache entries and result flags each action adds per
mode, the diagnostic count, and the production lookup's starting cache state
against the observed one. Native type/signature/instantiation counters are
reported beside the prototype's own lazy-record transitions, not compared:
they are representation differences by construction. `capture` runs parity,
then warmups and seven alternating samples per implementation for the normal
and allocation executables; `report` produces `run.relater.parity` (1 only when
both implementations match every case), `throughput_ratio` (ID over reference
relation time; >1 means the reference is faster), `allocated_bytes_ratio` and
`retained_bytes_ratio` (reference over ID), all declared as `[relater]` in
`status/runs.toml`. Timing ratios are unavailable while the two implementations
execute different group inventories.

### Parity at the current pin

| implementation | groups | matched | unsupported | parity |
|---|---|---|---|---|
| production ID relater | 105 | 105 | 0 | 1.0000 |
| reference prototype | 105 | 85 | 20 | 0.8095 |

The 20 unsupported groups are the five modes of `optional-rest-tuples` (tuple
references), `deferred-generic-members` (generic instantiation and variance),
`mapped-conditional-infer` (mapped type) and `template-literal` (template
literal type). Every group the reference executes matches the Go observation,
including the recursive, deep (64 to 4,096 levels), union, intersection,
index-signature and overload fixtures. Of the 340 first/repeat transitions the
Go counters record, the prototype's lazy records agree with 302; the rest are
groups where Go creates types or signatures during the relation (instantiation,
erasure) and the reference has nothing to create. `run.relater.parity` is
therefore 0.81, not 1: the reference relater does not cover the whole frozen
inventory, and the plan's gate stays unmet until it does or the owner records a
decision about the four fixtures.

A production observation from the reference's setup: resolving the property
types of the 4,096-level nested type literal costs about 7 s per group in the
Rust checker (`get_type_of_symbol` walks ancestors through per-node AST view
lookups), while the production relation interval stops at the 100-level
assumption limit and never pays it; the 64-level fixture, which does resolve
fully, relates in 43 ms. This is a production cost, not a P7 adapter cost, and
it inflates the reference's reported setup time.

### Smoke run (development host, 7 samples, not the measurement)

`scripts/s08_relater.py capture --smoke` completed both executables end to end.
Every sample repeated its own group inventory; the timing and allocation ratios
stay unavailable because the two implementations do not execute the same fixed
work (ID 105 groups, reference 85 executed and 20 unsupported). The raw totals,
for orientation only:

| quantity (sum over the groups each side executes) | ID | reference |
|---|---|---|
| setup (checker creation, lookup; reference adds translation and construction) | 2.98 s | 39.6 s |
| relation interval | 289 ms | 3.2 ms |
| relation requested bytes (allocation executable) | 88.3 MB | 13.4 MB |
| retained bytes at the after-checkpoints | 1.30 GB | 1.35 GB |

Two structural caveats make the relation column incomparable even on a shared
inventory. The translation resolves every reachable production type at setup,
so the reference's relation interval carries only its own lazy member
materialization, while the production interval also resolves structured
members, signatures and index infos for the first time. And the reference's
setup carries the production `get_type_of_symbol` cost noted above for the deep
fixtures. A fair comparison needs the reference to construct from the bound
program itself (its own lazy resolution of declarations), which is beyond an
isolated relater; the report states the incomparability instead of a ratio.

## What P7 still owes

- The measurement itself: `scripts/s08_checkerbench.py capture` and
  `scripts/s08_relater.py capture` on the designated quiet host, then
  `cargo xtask status --record`. The full checkerbench run is 48 processes
  over all variants; the Rust child shares one file cache across variants and
  keeps the previous variant's library files alive until the next program has
  loaded, so library parses are reused the way the Go harness caches parsed
  files (outside the interval; the retained files are live at both retained
  endpoints and in the after-release figure).
- The footprint decision (§6.1): if the ratio misses 0.80 on the full run, one
  integrated candidate from actual attribution, recorded with its complete
  comparison.
- Reference relater coverage of the four unsupported fixtures, or an owner
  decision recording the reduced inventory.
